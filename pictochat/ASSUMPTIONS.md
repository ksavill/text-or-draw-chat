# PictoChat codec assumptions

This package implements only the application data observed inside Nintendo DS
local-multiplayer CMD/REPLY traffic. It does not implement the 802.11 beacon,
authentication, association, CF-Poll timing, or acknowledgement layers needed
to communicate with a physical DS.

The format is reverse-engineered rather than an official Nintendo protocol:

- Multi-byte integers are little-endian.
- MAC addresses inside profile and drawing records have each 16-bit byte pair
  reversed. The public API accepts and returns conventional MAC byte order.
- Profile text is treated as fixed-width UTF-16LE/UCS-2-compatible data. This
  agrees with current captures, although older experimental code describes the
  encoding as unresolved. The encoder rejects overlong or embedded-NUL text.
- Profile bytes 82 and 83 are interpreted as birth month and birth day based on
  the current capture dissector. One experimental implementation labels these
  in the opposite order.
- Drawing data is 256 pixels wide, 4 bits per pixel, in row-major 8x8 tiles.
  The low nibble is the left pixel. Heights are 16, 32, 48, 64, or 80 pixels.
- The interactive DS area is 228 pixels wide. `x_offset=0` is only a provisional
  browser-to-backing placement. The DS also applies a non-rectangular display
  mask around the border and username. Confirm placement with a golden capture.
- Drawing records contain two 14-byte regions with unresolved semantics. The
  codec preserves both. Its metadata default comes from the current
  `foa_dswifi` experiment and should not be treated as a protocol constant.
- The first two Type 0/1 body bytes are exposed as `sender_id` and `data_type`
  for capture work, but those names are provisional: the pinned working
  firmware treats the same bytes as one little-endian console ID. The marker
  and trailing ten bytes are also preserved. The trailer may hold
  transfer/session identity, so `build_transfer` requires the caller to supply
  a value from validated bridge state rather than silently inventing it.
- Type 2's `transfer_flags & 1` is treated as the final marker. Default fragment
  payload types FF/97/04 and the 180-byte chunk size match the current working
  `foa_dswifi` experiment. They remain configurable and need physical-hardware
  validation, especially for multiple clients.
- Duplicate Type 2 fragments are ignored only when overlapping bytes agree.
  Conflicting retransmissions are rejected rather than guessed through.

Primary working references used for the layout are the `foa_dswifi` PictoChat
packet/application sources and the VSR PictoChat capture dissectors. Before a
real-console test, retain a known-good PCAP and compare every generated byte.
